Reading the Authentication-Results Header: RFC 8601 & ARC Forensics

Published by the TraceXMail team • Updated October 23, 2026

1. The Role of the Authentication-Results Header (RFC 8601)

When an email arrives at an inbound boundary Mail Transfer Agent (MTA), the receiving server evaluates multiple independent identity authentication frameworks. These include Sender Policy Framework (SPF, RFC 7208), DomainKeys Identified Mail (DKIM, RFC 6376), and Domain-based Message Authentication, Reporting, and Conformance (DMARC, RFC 7489).

To communicate these forensic conclusions down the delivery chain to downstream filters, spam engines, and Mail User Agents (MUAs), the border MTA stamps a standardized header specified by RFC 8601 (which obsoleted RFC 5451 and RFC 7001): Authentication-Results:.

Canonical RFC 8601 Syntax Example: 
Authentication-Results: mx.example.com;
  dkim=pass (test key) header.d=example.org header.b=abc1234;
  spf=pass (mx.example.com: domain of sender@example.org designates 198.51.100.25 as permitted sender)
    smtp.mailfrom=sender@example.org;
  dmarc=pass (p=REJECT sp=REJECT dis=NONE) header.from=example.org;
  arc=none

2. The Critical Trust Boundary: authserv-id

The first token immediately following Authentication-Results: is the authserv-id (in the example above, mx.example.com). This field defines the administrative boundary of the MTA that conducted the cryptographic tests.

An essential forensic principle for security analysts is that an incoming message may contain multiple Authentication-Results: headers. An attacker can craft arbitrary headers before transmitting an email through an open relay, injecting fraudulent spf=pass or dkim=pass statements.

Forensic Rule: Only inspect the Authentication-Results: header whose authserv-id matches the hostname of your own organization's perimeter gateway or trusted cloud provider. Any upstream header bearing a foreign authserv-id must be treated as unverified data unless secured by an unbroken Authenticated Received Chain.

3. Dissecting Individual Protocol Verdicts

Each protocol evaluated within the header contains a result token followed by reason parameters and identifier properties.

SPF Evaluation Results

  • pass: The connecting client IP is explicitly authorized by the sender's DNS SPF record.
  • fail: The client IP is explicitly not authorized (matching a -all mechanism).
  • softfail: The client IP is not permitted, but the domain owner specified a non-assertive ~all transition policy.
  • neutral: The domain SPF record takes no definitive stance (?all).
  • none: The envelope sender domain publishes no SPF TXT record.
  • permerror: The SPF record is syntactically invalid or exceeded the 10 DNS lookup limit.
  • temperror: A transient DNS resolution failure occurred during verification.

DKIM Evaluation Results

DKIM verifies that an authorized cryptographic key pair signed specific header fields and the message body. The header.d= parameter reports the signing domain, while header.b= shows the signature prefix:

  • pass: The digital signature is cryptographically valid and matches the public key retrieved from DNS.
  • fail: The signature verification failed, indicating that headers or body text were modified in transit or the key was revoked.
  • none: The message was delivered without a DKIM-Signature header.
  • permerror / temperror: The public key was malformed or DNS timed out during lookup.

DMARC Policy Enforcement & Alignment

A passing SPF or DKIM test is insufficient on its own to thwart brand spoofing. DMARC requires Identifier Alignment with the RFC 5322 visible From: header. In RFC 8601 headers, DMARC reports:

  • pass: At least one underlying protocol (SPF or DKIM) passed and aligned with the visible From domain.
  • fail: Neither protocol achieved aligned pass status. The header will include the applied policy disposition (e.g., dis=reject or dis=quarantine).

4. Authenticated Received Chain (ARC - RFC 8617)

When an email traverses intermediate systems—such as automated mailing lists, alumni email forwarders, or external compliance gateways—the intermediate MTA typically alters the message body (appending footers) or forwards the message from a new IP address. This legitimately breaks SPF and invalidates original DKIM signatures.

RFC 8617 introduces the Authenticated Received Chain (ARC) to preserve authentication status across intermediaries. An ARC sequence consists of three header sets numbered by instance:

  1. ARC-Authentication-Results (AAR): A snapshot of the RFC 8601 results recorded at that specific hop.
  2. ARC-Message-Signature (AMS): A cryptographic signature covering the message headers and body.
  3. ARC-Seal (AS): A signature sealing all previous ARC headers into an immutable cryptographic chain.
ARC Evaluation in Authentication-Results: 
arc=pass (as.1.example.org=pass, ams.1.example.org=pass)

When arc=pass, the receiving gateway recognizes that even though intermediate forwarding broke direct SPF, the initial sender authenticated successfully at the origin boundary.

5. Summary Comparison of Verification Headers

Protocol Tested Identity Primary Failure Indicator Security Risk
SPF RFC 5321 Return-Path (Mail From) spf=fail or spf=softfail Unauthorized mail server or forged relay IP.
DKIM Cryptographic d= domain signature dkim=fail (bad signature) Message tampering in transit or key compromise.
DMARC Alignment with RFC 5322 From header dmarc=fail (p=reject) Direct brand impersonation and spoofing.
ARC Prior intermediate hop signatures arc=fail Broken relay custody chain or corrupted forwarder.
