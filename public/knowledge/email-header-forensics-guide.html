The Definitive Guide to Email Header Forensics & Hop Traceroutes

Published by Jayaram Sappa • Lead Security Researcher • Updated October 2026

1. The Anatomy of an RFC 5322 Internet Message

Every email delivered across the Internet consists of two fundamental sections separated by an empty newline: the header block and the body block. While common email clients (such as Microsoft Outlook, Apple Mail, and Gmail) render only the subject line and sender display name, the raw headers contain the forensic chain of custody.

Because each intermediate Mail Transfer Agent (MTA) appends its own Received: header to the very top of the message, the transmission history must be parsed in reverse chronological order:

  • Top-most Received header: The final hop (the recipient's internal mail server).
  • Bottom-most Received header: The initial origin hop (where the message entered the public SMTP relay chain).

2. Dissecting the Received: Header Syntax

According to RFC 5322 Section 3.6.7, a standard Received: header contains several standardized clauses:

Example Canonical Received Header: 
Received: from mail-relay1.attacker-domain.com (outbound.isp.net [198.51.100.45])
  by mx.google.com with ESMTPS id abc123xyz
  for <victim@company.com>
  (version=TLS1_3 cipher=TLS_AES_256_GCM_SHA384);
  Thu, 08 Oct 2026 14:22:10 -0700 (PDT)

Crucial Forensic Fields

  • from [HELO/EHLO string] ([Reverse DNS hostname] [IP Address]): Identifies the client sending the message. Threat actors often forge the HELO string (e.g., claiming to be google.com), but receiving MTAs record the physical TCP socket IP in brackets.
  • by [Receiving Server]: The identity of the MTA receiving the packet.
  • with [Protocol]: The transport protocol used (e.g., ESMTPS for authenticated encrypted delivery).
  • id [Queue ID]: Internal message queue tracking identifier.
  • for <Recipient>: The envelope RCPT TO destination.
  • Timestamp: Date and time with timezone offset indicating exact ingress time.

3. Spotting Forged & Injected Headers

Because threat actors have complete control over the email client before sending, they can pre-populate arbitrary Received: headers in the raw payload before injecting the email into an SMTP server.

Forensic Rule of Custody:

You can only trust headers appended by servers under your organization's administrative control or verified reputable upstream MTAs (e.g., Google Workspace, Microsoft 365, Proofpoint).

To identify forged hops:

  • Time Travel Anomaly: If Hop 2 has a timestamp later than Hop 3, the timeline is mathematically impossible and indicates injected headers.
  • IP Discrepancy: If a lower hop claims to receive a message from an IP that has no corresponding route or reverse DNS record matching the server's identity.
  • Missing Queue Identifiers: Injected mock headers often omit authentic MTA queue IDs or TLS cipher specifications.

4. Calculating MTA Hop Traversal Delays

In modern cloud email infrastructure, standard delivery latency between MTAs typically ranges between 100 milliseconds and 3 seconds. An unexplained delay of several hours between hops usually signals one of three conditions:

  1. Greylisting: The receiving server deferred the message intentionally to combat spambots.
  2. MTA Quarantine or Sandbox Detonation: The message underwent deep sandbox file analysis.
  3. Offline Compromise: An attacker held the email on a staging relay to coordinate a multi-stage spearphishing campaign.
